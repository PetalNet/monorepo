# Grove UX

**Status:** Focused implementation view  
**Normative source:** `01-GROVE-BUILD-SPEC.md`

This document describes what using Grove should feel like and how the principal workflows behave. It does not create independent domain rules.

## 1. Experience promise

Grove should feel like a shared, intelligent workspace that gets out of the user's way:

- start from one private Ask/Capture control;
- make the system's interpretation visible before action;
- turn real work into a comprehensible Task plan;
- let humans and agents collaborate without turning chat into an operations log;
- bring the user in only when their judgment or authority is required;
- preserve useful output so it becomes easy to find and cite later.

The user should not need to understand fleets, leases, event buses, workflow engines, model providers, or graph storage to complete ordinary work.

## 2. Top-level experience

### Home

Private starting point for:

- Ask/Capture;
- Needs You;
- Continue;
- pins and saved personal views.

### Library

Universal navigation and shared information field:

- search or ask;
- open Projects, Tasks, Rooms, Agents, people, documents, artifacts, and Topics;
- browse backlinks, related work, versions, and provenance;
- use saved views and collections.

### Admin

Authorized operational experience:

- agents and Runtimes;
- hosts and services;
- models, providers, and cost;
- observability and signals;
- networking, updates, security, and terminal.

Admin extends the current console surfaces. It is not the ordinary participant's starting point.

## 3. Ask/Capture

Ask/Capture begins private and user-scoped.

As the user types, Grove infers a candidate intent and shows it in an editable preview:

```text
Ask Personal Librarian · Private
```

```text
Create Task in Oak · Grove
```

```text
Research · Current Room and linked Task · Starts on send
```

```text
Publish to Grove · Confirmation required
```

Rules:

- intent inference does not silently widen permissions;
- ambiguous language falls back to a private response;
- deterministic controls remain available;
- state-changing or externally consequential actions follow policy;
- the user can inspect context, capabilities, destination, model/cost class, and launch behavior.

## 4. Home attention

One adaptive region appears beneath Ask/Capture.

### Needs You

Only when Grove cannot safely continue, conclude, or meet a commitment without the user:

- approval or decision required;
- missing information or access;
- required review ready;
- recovery exhausted;
- security/privacy/spending boundary reached;
- commitment at risk;
- direct response requested by another person.

Each item says:

- what is needed;
- why;
- what happens if ignored;
- the exact action or object that resolves it.

It resolves automatically from authoritative state. Users may act, delegate, snooze, decline, or change policy. A generic dismiss cannot hide an unresolved obligation.

### Continue

When no action is required, show a small set of pinned or recently meaningful Rooms, Tasks, Projects, and investigations.

### All caught up

When nothing requires attention or useful continuation:

```text
All caught up.
```

Grove does not invent alerts, suggestions, or engagement loops to fill the screen.

## 5. Starting and running a Project

### Create

The user writes an Ask and chooses or confirms `Create Project`.

Grove creates a Project-role Task with:

- purpose;
- responsible human;
- privacy/publication policy;
- completion contract or standing responsibility;
- initial source references.

### Brief

The Grove Librarian assembles:

- relevant prior work;
- current preferred sources;
- related decisions and artifacts;
- contradictions;
- known gaps;
- useful Agents, tools, and capabilities.

### Plan

A Planner creates a draft Task DAG.

The plan makes visible:

- Tasks and dependencies;
- parallelizable branches;
- human decisions;
- approvals and reviews;
- tools/hosts/models required;
- expected outputs;
- blockers and assumptions;
- what “done” means.

### Grill

If the Ask is unclear, Grove opens a bounded grilling session rather than inventing requirements.

The session may be:

- private with the user;
- in the Project Room;
- with named stakeholders.

Answers update the Task plan through explicit operations. The conversation remains linked to the resulting Task Versions.

### Execute

Ready Tasks fan out to eligible Agents, humans, or automations.

The Project page shows:

- what is ready;
- what is running;
- what is blocked;
- what is waiting for review;
- what needs the user;
- outputs as they become durable.

Routine tool calls and retries remain behind the relevant Attempt.

### Review and close

Results enter Review when the completion contract requires it.

For code:

- pushed commits;
- required checks;
- linked PR;
- independent review;
- merge to the configured branch.

For research or documents:

- exact output Version;
- citations and sources;
- review/approval policy.

The Task completes only after verification accepts it.

### Contribute

Accepted durable outputs enter their authorized Library realm with:

- exact Versions;
- originating Project/Task/Attempt;
- sources and citations;
- responsible human and Agents;
- trust/freshness status;
- relationships to existing Topics and work.

Grove-realm Project outputs contribute to shared Grove knowledge under policy. Personal Project outputs remain Personal until the user explicitly publishes them or has configured a standing publication policy.

## 6. Rooms

### Purpose

A Room is a human-readable collaboration context anchored to one Task branch.

It may be:

- human-only;
- invoke-only;
- assisted;
- collaborative with attached Agents;
- an intentional agent workshop.

Human-oriented Rooms default to invoke-only.

### Broad and narrow Rooms

An Oak General Room may anchor to the Oak Project Task and coordinate many Task lanes.

When one lane needs a distinct audience, history, permission profile, or sustained focus, it may branch into a narrower Room anchored lower in the Task DAG.

Rooms do not create a second work hierarchy.

### Timeline

The Room timeline contains:

- human messages;
- deliberate Agent messages;
- questions, blockers, proposals, decisions, results, and handoffs;
- concise projections of significant accepted Task operations.

It does not contain routine:

- claims and renewals;
- heartbeats;
- RPC;
- tool calls;
- retries;
- scheduler activity.

These remain inspectable through Tasks and Admin.

### Official actions

Conversation is free and self-directed.

- Humans use explicit Grove controls.
- Agents use MCP/domain tools.
- Automations use typed commands.

Grove never treats “I will take this” as a successful Claim until the Task authority accepts a deliberate claim operation.

### Results

A Room-visible Agent returns its final result visibly to the Room.

The result message links to the Task and output Version. Context, tools, retries, evidence, and model details are expandable from the Task.

Private UI-agent results return privately and are shared only by explicit publication.

## 7. Agent invocation and presence

### Invocation

One bounded Task. The composer previews:

- Agent/role;
- context grant;
- capabilities;
- output;
- duration/cost;
- launch policy.

### Temporary presence

The Agent remains for a time, message count, meeting, or Task:

```text
Take notes for this meeting.
Stay for 30 minutes.
Participate until Task X enters Review.
```

The lease is visible and expires automatically.

### Standing attachment

One named Agent becomes a continuing participant with explicit role, context, speech, capability, retention, and revocation policy.

### Approval model

Room policy classifies operations:

- Automatic;
- Notify;
- Confirm;
- Denied.

Grove asks again only when an Agent crosses a meaningful policy boundary.

Even permissive Rooms show quiet persistent presence, significant-action receipts, and immediate pause/revoke controls.

## 8. Membership and history

Room membership grants conversation access only.

History policy is visible before joining:

- full;
- from join;
- recent window;
- curated summary and selected messages;
- none.

The Room creator is the initial Steward. Steward authority is capped by anchor Task governance.

If a Room becomes stewardless:

- allowed conversation may continue;
- membership/policy/lifecycle changes freeze;
- governance appoints a new Steward.

## 9. Matrix interoperability

Authorized people may use:

- Grove's first-party Room UI;
- a compatible Matrix client;
- an existing federated Matrix account.

Generic clients receive standard chat, replies, reactions, attachments, and human-readable results where possible.

Grove-native controls remain in Grove:

- Task DAG;
- reviews and approvals;
- private UI agents;
- rich invocation previews;
- Library/provenance;
- host/model/admin.

Matrix identity is not Grove authorization. Each Site grants access explicitly.

## 10. Private user agents

Personal Librarian, General, graphing, and other UI agents:

- belong to one user;
- have separate identities;
- work under a private Task branch;
- receive minimum-sufficient context;
- do not automatically join Rooms;
- retain memory under user policy;
- publish selected snapshots, not private histories.

Opening a private assistant from a Room may give it a pinned Room/message reference, but not ambient access to the complete Room.

## 11. Empty, loading, stale, and failure UX

- Loading uses shape-matched skeletons, not idle spinners.
- A spinner appears only during real polling or streaming.
- Empty states are truthful and quiet.
- Stale state is visibly stale.
- Actions on stale authority block; recovery actions remain available when the executor is healthy.
- Offline state uses in-place degradation and a quiet snackbar, not a modal.
- P0 failures are fact-first, show blast radius, and provide the relevant recovery action.
- No flavor or lore may obscure danger.

## 12. UX acceptance

The UX is ready when a non-technical user can:

1. create a Project from Ask/Capture;
2. understand or correct the proposed plan;
3. join or create a Room;
4. invoke an Agent with visible scope;
5. see what is running without seeing operations noise;
6. provide a required decision from Needs You;
7. review the exact result;
8. find and cite the accepted output later;
9. understand whether information is private, Grove-shared, or explicitly restricted;
10. use the core flow without learning fleet infrastructure.
